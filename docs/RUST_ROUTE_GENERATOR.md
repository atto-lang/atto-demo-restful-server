# Rust route generator migration

This independent host tool generates the existing legacy `.ores` route registry and configuration. It intentionally **does not** claim native `.atto` compiler support, actor execution, HTTP transport, AOT equivalence, or backend parity.

Run `bash scripts/generate-routes.sh --port 3000 --data-dir data` to publish `src/generated/routes.ores` and `config.ores` through atomic single-file replacements. `cargo test --offline --locked --manifest-path tools/route-gen/Cargo.toml` exercises discovery, path admission, symlink rejection, last-good preservation, JSON encoding, and deterministic ordering. Production `scripts/run-server.sh` and `scripts/build-native.sh` now invoke the Rust wrapper. The CI parity gate compares the output bytes with the existing Python oracle using the same concrete route and data directory inputs; the Python tests stay until equivalent Rust fixtures are independently reviewed.

Fail-closed limits: 10,000 directory entries, 64 directory levels, and 4,096 routes; no symlink or special device in the route tree, no external route root or output-directory alias, no unsafe path segments, and a nonzero TCP port. No network access or Python interpreter is needed for the Rust generator. The publisher now preflights **both** output leaf types before writing either, preventing deterministic partial replacement when a leaf is a directory or special file. Individual files are replaced atomically; the two-file output pair remains **nontransactional** if a write or rename fails after preflight. A grouped-publication transaction is separate work.

### Descriptor-relative filesystem hardening and remaining boundaries

On **Linux**, production route discovery and publication now use pinned directory descriptors. The source tree is opened component-by-component with `openat(O_NOFOLLOW)`, including source files inspected with nonblocking `O_PATH` metadata. Directory enumeration is through the pinned `/proc/self/fd/N` inode, subject to the 10,000-entry / 64-level bounds. The output directory is pinned independently; preflight checks and `renameat` operate within its descriptor, with file and directory `fsync`. Four focused Linux tests demonstrate safe behavior when a pinned source or output ancestor is renamed and replaced by an attacker-controlled symlink, when a source leaf is a symlink, and when the second output leaf is a directory. This is **not** a full proof against arbitrary concurrent mutation.

The caller-supplied **project root and its path ancestors** must be trusted; the configured `--data-dir` continues to use standard library directory creation and canonicalization. In-place modifications by an attacker who already holds write permission on a pinned directory, such as swapping a temporary leaf or modifying guest source bytes after enumeration, are still out of scope. The caller must not use elevated privileges or a concurrently attacker-writable checkout/output directory. A fully adversarial publisher would require stronger ownership/permission constraints and isolated staging, not merely directory descriptors. The two output files remain distinct atomic renames rather than a single atomic transaction.

On **non-Linux hosts** the existing portable standard-library publisher remains in use for compatibility. It prevents *static* symlink traversals but **does not** have the descriptor-relative path-redirection guarantees. A platform-native descriptor-relative backend is a separate task.

The descriptor-relative implementation has no external Rust dependencies. Linux requires `/proc/self/fd`; a missing or inaccessible procfs makes the generator fail closed rather than silently falling back to the path-based implementation.
